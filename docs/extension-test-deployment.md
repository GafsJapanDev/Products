# 第2段階：別アプリでの拡張テスト

このブランチはテスト専用。現行GASやmainへ上書きしない。
編集はGitHub上のみ。実行検証はコードをメモリに読み込んで行っており、PC上のソースファイルは編集していない。

## 変更ファイル

- Code.gs：既存保存処理を維持し、テスト先チェック、LINEサーバー停止、伝票集計、ジャーナル原本ID保存を追加。
- Index.html：既存4タブを維持し、追加画面をテンプレートで読み込む。
- ExtensionStore.gs：テスト環境初期化、履歴保存、再送・版管理。
- ExtensionPurchases.gs：伝票・明細・品目・月末税額・月別帳票。
- ExtensionAssistant.gs：読み取り専用検索、Cloudflareの関数選択、定型検索。
- ExtensionOcr.gs：画像・PDF原本保存、Drive v3 OCR、印字ラベル対応。
- ExtensionInventory.gs：月末棚卸、単価・換算、確認依頼・2名確定・再確認。
- Extension.html / ExtensionClient.html：追加タブのHTMLとJavaScript。
- appsscript.json：Drive API v3、ドキュメント権限。
- tests/extension.test.cjs：依存ライブラリなしのNodeテスト。

Deposit.gsは変更不要。元のコードのまま同じプロジェクトへ追加する。

## テストアプリの配置

1. Google Driveの「99_System」などで**新しいApps Scriptプロジェクト**を作る。名前を「かさ原 日報・AI 拡張テスト」とする。
2. このブランチのCode.gs、Deposit.gs、Extensionで始まる5つの.gs、Index.html、Extension.html、ExtensionClient.htmlを同名で配置する。
   - 追加.gsはStore / Purchases / Assistant / Ocr / Inventoryの5つ。Code.gsとDeposit.gsを合わせて.gsは計7つ。
   - HTMLを追加するときは種類「HTML」、名前はIndex / Extension / ExtensionClient。
3. プロジェクトの設定でappsscript.json表示を有効にし、このブランチのmanifestへ置き換える。
4. サービスにDrive API v3が表示されることを確認。標準Google Cloudプロジェクトを自分で指定している場合は、そのプロジェクトでもDrive APIを有効にする。課金契約は追加しない。
5. **新しいプロジェクトのスクリプトプロパティ**へ次だけ設定する。
   - TEMPLATE_ID：既存ひな形のスプレッドシートID。
   - TEST_IMPORT_MONTHS（任意）：本番の月別台帳をコピーして試す場合。例：{"2026-10":"コピー元10月台帳ID","2026-11":"コピー元11月台帳ID"}
   - FOLDER_ID、MONTH_年月、EXTENSION_BOOK_ID、LINE用設定は貼り付けない。
6. 関数setupExtensionTestをエディタで1回実行し、Googleの権限を許可する。テスト専用フォルダ・拡張台帳を新規作成し、指定した月別台帳はコピーする。コピー元は更新しない。
   - 実行ログのフォルダURLと拡張台帳URLを保存する。
   - 自動作成する設定：APP_ENV=test、TEST_ROOT_ID、FOLDER_ID、EXTENSION_BOOK_ID、LINE_DISABLED=true、コピー先のMONTH_年月。
   - 途中失敗で設定が残った場合は既存プロジェクトへ初期化を再実行せず、作成先を確認して新しいテストプロジェクトでやり直す。
7. 「デプロイ」→「新しいデプロイ」→「ウェブアプリ」。実行ユーザーは自分、アクセスは自分のみ。テストするiPadも同じGoogleアカウントで開く。公開範囲を「全員」へ広げる必要はない。
8. 新しい /exec URLを開く。「拡張テスト版／LINE送信停止中」を確認する。
9. 更新は「デプロイを管理」→鉛筆→バージョン「新バージョン」→デプロイ。保存しただけでは/execへ反映されない。

テストビルド定数がtrueの間は、画面のLINEチェックやトークン設定の有無に関係なく送信関数が停止する。
本番と同じFOLDER_IDを指定したり、本番MONTH_設定をコピーすると、テスト用所有先チェックで操作を拒否する。

## Cloudflare：後から設定してよい

手入力、伝票保存、OCR、棚卸、定型検索はAI設定なしで使える。

Cloudflare Workers AIをFreeプランで用意し、対象アカウントでWorkers AIのRead権限を持つAPIトークンを作成。
GASのスクリプトプロパティへCF_ACCOUNT_IDとCF_API_TOKENを設定する。秘密情報をGitHubやHTMLへ貼らない。
Gemma 4 @cf/google/gemma-4-26b-a4b-itをGASから直接呼ぶ。別Worker・有料ホスティングは作らない。
無料枠を超えたらAIを停止し、定型検索へ案内する。有料APIへの切り替えはない。
Freeプランのまま使い、支払いを伴うプラン変更を行わない。
この実装ではAIは検索条件と関数を選び、回答の数字と表はGAS結果から直接描画する。モデルによる再計算を行わない。

## 追加シートと保存の扱い

既存内部4記録と既存帳票は残す。拡張台帳の「変更履歴」を正本とし、1操作の伝票ヘッダー・全明細を1つのJSONイベントで保存する。
これにより、ヘッダーだけ保存され明細が途中までになる状態を避ける。
他の追加シートと月別台帳内の追加シートは再生成できる表示用シート。
表示用シートを手修正しても、再集計すると元に戻る。修正はアプリから行う。
履歴シートは手編集しない。再集計はrebuildExtensionViews。

| シート | 主な列 |
|---|---|
| 変更履歴（拡張台帳のみ） | 操作ID、種別、ID、版、日時、入力ハッシュ、JSON |
| 納品伝票 | 伝票ID、版、納品日、仕入先、伝票番号、種別、状態、税区分、印字額、税額、記録合計、食材、飲料、雑費、容器、明細状態、原本、理由 |
| 仕入明細 | 伝票ID、状態、納品日、仕入先、品目ID、商品コード、品名、数量、単位、単価、明細金額、税区分、税率、分類、理由 |
| 品目台帳 | 品目ID、仕入先、商品コード、品名、棚卸単位、検索別名、換算JSON |
| 月締税額 | ID、対象月、仕入先、食材税額、飲料税額、雑費税額、状態、備考 |
| 棚卸 | 対象月、基準日、版、状態、再確認、実施者、確認者、確認依頼日時、確定日時、品目ID、仕入先、品名、数量、単位、税込単価、金額、連続ゼロ月数、単価採用元 |
| 原本管理 | ID、対象月、ファイル名、原本URL |
| 売上報告（既存へ1列追加） | 既存列の後にジャーナル原本ID |

- 操作履歴JSONには原本ID・簡易入力の対応・各明細・設定・過去版も保持する。
- 伝票番号や商品コードの先頭0は文字列のまま保持する。
- 仕入先名・商品コード（なければ品名）から品目IDを決定する。同名の別仕入先は別ID。
- 元の簡易入力を選んで伝票化した場合は、その額を差し引いて伝票分へ置換する。連携済みの簡易入力は伝票タブから修正する。
- 西原の雑費は納品伝票の雑費欄へ分け、仕入れ食材欄や小口現金出金へ混在させない。
- カクヤスの容器回収は正の返金額を入力し、種類「容器回収・返金」でマイナス計上する。
- 月末税額は月末加算の伝票のみを対象に登録する。対象伝票を修正すると税額を要再確認とし、古い税額を集計へ足さない。
- 原本はテスト保存先内の原本_yyyy-MMへ格納。伝票取消でも削除しない。
- 原本1ファイル8MBまで。JPEG・PNG・PDF。iPadのHEIC画像はJPEGへ変換して添付する。

## iPadでの確認手順

1. 売上・簡易仕入れ・小口・入金を入力。0円・0人も保存し、現行本番の台帳に変化がないこと、LINE投稿されないことを確認。
2. 納品伝票：2品目を入力、片方を外して保存、修正、取消、再読み込み。簡易仕入れの既存行を選んで伝票化し二重計上がないことを確認。
3. 帳票読取：ジャーナル写真を選択→原本保存・OCR→原文と候補を確認→確認チェック→売上フォームへ反映。印字総売上と決済合計、税額、会計回数、人数を確認してから保存。
4. キタニはPDF、maruyasuは複数ページを一度に選択。合計未取得は手入力。読取後、納品伝票フォームで日付・税区分・伝票合計・明細を修正して保存。
5. 西原の食材・雑費を分ける。カクヤス容器回収は返金額を確認し種類・分類「容器」で入力。
6. 棚卸：対象月を選ぶ→一覧→数量入力→下書き→実施者と別の確認者を選択→確認依頼→確認者が確定。翌月操作でも基準日は対象月末であることを確認。
7. 単位が違う品目は品目台帳へ換算を登録する。例：棚卸kg、仕入れ箱なら{"箱":10}は1箱=10kg。
8. AI設定前に定型検索を使用。設定後に単価・3か月推移・複合質問を試す。曖昧な仕入先・データなし・0円・明細なしも確認。
9. CF_API_TOKENを一時的に外し、AIエラー表示中も保存・棚卸・定型検索が使えることを確認。

## 第3段階：現行反映と戻し方

別テストが完了し結果を共有するまで実施しない。

1. 本番GASソース、スクリプトプロパティ、本番月別台帳、ひな形をバックアップ。現行デプロイのバージョンを記録する。
2. 本番用の拡張台帳・原本保存先を用意し、データ移行をテストコピーでリハーサル。テスト伝票・在庫・月別コピーを本番へ移さない。
3. ExtensionStore.gsのテスト定数を本番向けに変更する別コミットをレビューする。テスト初期化関数を本番で実行しない。
4. 本番用EXTENSION_BOOK_IDと原本フォルダを設定。TEST_ROOT_ID/TEST_IMPORT_MONTHSなどテスト専用値を持ち込まない。既存MONTH_設定は保持。
5. 本番反映直後はLINE_DISABLED=trueのまま最小確認。その後既存LINE設定を使い、意図した通知のみ再開する。
6. 新しいバージョンで既存デプロイを更新する。
7. 問題時は既存デプロイをバックアップした旧バージョンへ戻す。コードだけでなく、移行後の書き込み有無を確認して台帳・プロパティの復旧を判断する。拡張履歴と原本は消さない。

このブランチには本番切り替え処理や本番LINE再開を含めていない。
